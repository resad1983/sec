你在终端敲下一句话，它内部到底经历了什么？

## 从一句话开始，拆出整条链路

我输入了这么一句。

帮我搜集今天的热点新闻，每条要分类，附上简要分析。

看起来平平无奇，但拆开来看，至少要完成搜索、分类、分析、格式化四件事，涉及多轮工具调用，可能还得并行跑子任务。

Hermes 把这条消息从头送到尾，经过了五层。

入口层（CLI + 20 多个平台适配器）、网关层（会话管理）、执行层（AIAgent 主循环）、扩展层（工具、技能、子 Agent）、存储层（SQLite + 记忆文件）。

每一层各司其职，每过一层都被加工一次。

## 主循环的三个退出方式

执行层是心脏。

核心逻辑其实就一个 while 循环，模型推理一轮，看有没有工具要调，有就执行，没有就把结果还给用户。

但魔鬼在细节里。

这个循环有三种退出方式，模型直接给了最终文本（正常结束）、迭代预算耗尽（硬上限，防止烧穿 token）、用户按了 Ctrl+C（优雅中断，不是粗暴 kill）。

父 Agent 上限 90 轮，子 Agent 50 轮。

每推理一轮扣 1 次预算，不管这轮并行调了几个工具。

有意思的是退款机制，如果这一轮模型只调了 `execute_code` （也就是写了一段 Python 脚本，脚本内部自己串联多个工具），刚扣掉的 1 次会被退还。

为什么？因为 PTC（程序化工具调用）本身就是效率怪兽。

普通方式做 8 次信息获取，要 8 轮模型推理；PTC 一轮写完脚本，脚本自己跑完 8 次。

系统再把这 1 轮也免掉，脚本执行在预算里等于零成本。

90 轮预算就能全部留给真正需要推理的环节。

## 子 Agent 委托，只传任务描述，只返回最终摘要

回到那个新闻例子。主 Agent 不会自己一条条去搜科技新闻、财经新闻、国际新闻，它会调 `delegate_task` ，fork 出几个子 Agent 并行跑。

子 Agent 有自己独立的上下文和 50 轮预算，父子之间只通过任务描述和最终摘要通信。

中间过程？父 Agent 完全看不见。

这不是偷懒，是刻意设计。

主 Agent 的上下文越干净，能撑的用户对话轮数就越多。

把重活甩出去，只收一句摘要回来，等于用并行开销换主 Agent 的长寿命。

子 Agent 被禁了五个工具，不能再委托（防套娃）、不能反问用户（用户不在场）、不能写共享记忆（防噪声污染）、不能直接发消息（对外沟通只走父 Agent）、不能用 PTC（独立预算够用，不需要折叠）。

还有个细节，父 Agent 每 30 秒给子发心跳。

父被中断或者挂了，心跳断开，子 Agent 连锁停下。没这个机制，用户按了 Ctrl+C，后台还有一堆子 Agent 在默默烧钱。

## 记忆不是数据库，是快照

Hermes 的记忆系统出乎意料地克制。

两个文件，MEMORY.md 是 Agent 自己的笔记（这台机器 Python 是 3.11），USER.md 是对用户的了解（偏好、习惯）。

字符数硬限制，分别 2200 和 1375。

关键设计，记忆在会话开始时注入系统提示词，之后整个会话期间不再更新。

会话中通过工具写入的新记忆会立刻存到磁盘（不丢数据），但系统提示词里的快照纹丝不动。

下次新会话才加载最新版本。

为什么？前缀缓存。系统提示词是发给模型的第一坨内容，只要前缀不变就能命中缓存，省钱省时间。每轮写记忆都改系统提示词，缓存就废了。

这是用一致性换性能的工程权衡。不优雅，但管用。

## 自进化的秘密，你看不见它学，但它一直在学

这是 Hermes 最让我觉得有意思的地方。

用户看完回复，Agent 表面闲下来了。但在后台，它还在干活。

每消耗 10 次模型推理轮次，系统会在后台线程里 fork 一个 mini Agent，喂给它整段对话，任务只有一个，回顾刚才的过程，有没有试错过、改过主意、或者发现了非平凡的方法？有就写成技能存下来，没有就退出。

这个复盘线程有两条铁规矩，必须在回复已经发给用户之后才启动，绝不和用户正在等的响应抢资源； `quiet_mode=True` ，输出不回显给用户。

同时系统提示词里还有主动引导，告诉模型复杂任务完成后主动存技能。两条信号并行，模型自己主动存是理想情况，后台复盘是防它漏掉的保险。

技能越攒越多，下次遇到类似任务，Agent 从技能索引里找到现成方案，不用从头摸索。这就是自进化真正发生的地方。

## 上下文压缩不是删历史，是分层存档

对话太长会撞到模型上下文窗口的上限。Hermes 的压缩策略不是简单砍掉旧消息，而是分层处理。

压缩触发时，当前 session 的原始对话完整保留在数据库里不删，然后开一个新 session，把摘要作为起点， `parent_session_id` 指回旧 session。连续压缩几次就形成一条链，一路能追溯到最初的对话。

模型看到的是压缩版（省 token），数据库存的是完整版（不丢信息）。

用户问昨天你说的那个函数名叫什么， `session_search` 工具直接从老 session 的原文里搜出来。

但要注意一个微妙的区别，能搜到历史，不等于 Agent 记住了。搜索结果只是当次推理的临时上下文，不会自动沉淀为记忆。

真正持久的记忆只有一条路，模型主动调 `memory` 工具写入。

session 链保的是原始数据不丢，记忆系统保的是经验沉淀不丢。前者是被动存档，后者是主动学习。

两条通道各管各的。

## 工程决策背后的统一逻辑

读完整条链路，回头看会发现一个一致的设计哲学， **把矛盾拆到不同层去各自解决，而不是在同一个地方硬做取舍。**

前缀缓存和记忆更新矛盾？冻结快照解决。

省 token 和不丢历史矛盾？模型层压缩、数据层完整保留。

用户体验和自进化矛盾？主线程服务用户、后台线程默默复盘。

这些决策单独看都不复杂，但组合在一起，形成的是一个能长期运行、持续变聪明、同时不会烧穿预算的系统。
