這篇超過 17,000 字內容不是理論筆記，而是我自己在一段時間內， **實際用 Codex 跑過大量任務、踩過不少坑、反覆調整做法之後，才慢慢沉澱出來的一套工作流程** 。

我發現，Codex 要真正用得穩，不是在開頭把請求文件寫得有多詳細，也不是一開始就把框架定得有多完整。真正決定它好不好用的，反而是你 **能不能在不同階段給它正確的工作方式** 。

什麼時候先分析，什麼時候先設計，什麼時候先測試，什麼時候應該停下來等你確認，什麼時候可以交給它繼續往下跑。當這些節奏和邊界都建立起來之後，Codex 才會從一個偶爾靈偶爾失控的工具，變成真正能融入日常開發的助手。

所以這篇內容的目的，不是教你多幾句花巧 prompt，而是把我實際用下來 **最有效、最可控、最值得保留下來的方法，整理成一套在開發過程中每一個階段，你可以直接拿來套用的 Codex 實戰工作流。**

以下這 11 個階段 42 個技巧及提示，並不是我隨手整理出來的 prompt，也不是彼此割裂的零散方法。我會依照一個任務在真實開發過程中的推進順序來整理，從開始之前的 **需求分析與風險控制，到設計、開發、測試、驗收、分工、版本管理、知識沉澱，以至最後的自動化與交付控制，** 逐步拆解說明。

你可以把它理解為 42 個技巧，但更準確地說， **它其實是一套在開發每一階段都能駕馭 Codex，** 真實開發流程之中的實戰操作方法。

---

## 內容目錄

**階段一：開始任務前，先控住方向**
1.1 先叫 Codex 畫施工圖
1.2 先列出不確定的地方
1.3 用反向限制避免它亂改
1.4 先讀懂系統，再動手
1.5 改之前先分析影響範圍
1.6 先建立不改清單

**階段二：設計與視覺先行**
2.1 用 Image Gen 先做介面草圖
2.2 先生成開發路線圖圖片
2.3 圖像先定風格，代碼跟著走

**階段三：開發中，讓 Codex 自己驗收**
3.1 邊做邊測
3.2 先寫測試再寫功能
3.3 測試失敗時，不要盲目改測試
3.4 讓它用壞情境測試
3.5 先找最小可重現案例
3.6 卡住時直接接手調試
3.7 逐步模擬程式流程

**階段四：讓 Codex 真的看畫面與操作流程，Annotating、Browser Use 與 Computer Use 進階應用**
4.1 用 Browser 做前端肉眼驗收
4.2 用標注功能把 UI 問題變成明確修改
4.3 用 Computer Use 測原生 App 或無 API 工具
4.4 讓 Codex 操作真實瀏覽器測試

**階段五：Worktree 並行開發**
5.1 同一需求開兩條路線
5.2 一個 agent 做功能，一個 agent 做 review
5.3 一個 agent 讀架構，一個 agent 寫測試

**階段六：Subagent 專用提示**
6.1 使用 subagent 前先定清楚分工

**階段七：Git 與版本管理**
7.1 讓 Codex 主動管理 Git 節奏
7.2 高風險任務先產 patch，不直接套用
7.3 用三個視角檢查同一個改動

**階段八：Skills 沉澱工作流**
8.1 好流程直接變成 Skill
8.2 做專案專屬 Skill
8.3 Skill 不要寫成萬能工具

**階段九：文檔與記憶沉澱**
9.1 收工前更新接手文檔
9.2 長 thread 結束前先壓縮上下文
9.3 把硬規則寫進 AGENTS.md
9.4 Memory 只放個人偏好，不放專案硬規則

**階段十：Automations**
10.1 先 Skill，後 Automation
10.2 用 Automation 做每日工程 Brief
10.3 讓 Automation 跑在獨立 Worktree
10.4 用 Automation 回顧自己的 Codex 工作流

**最後一章：給 Codex 裝保險絲**
11.1 固定回報格式，不要長篇解釋
11.2 小步交付，不要一口氣做完
11.3 用時間盒限制過度設計
11.4 交付人類驗收清單
