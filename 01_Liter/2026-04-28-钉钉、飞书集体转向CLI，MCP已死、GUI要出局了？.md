## 核心洞察
AI Agent 時代的到來，正在深刻重塑軟體的介面邏輯。GUI（圖形使用者介面）是為了適應人類「一眼看全」的視覺習慣而生，但對 AI 來說卻是資訊過載且極不穩定的災難。各大平台（如釘釘、飛書）轉向 CLI（命令列介面）改造，本質上是將深埋在 GUI 背後的能力，重構為「可組合、可文本化、可被模型呼叫」的標準動作。未來，人類繼續用 GUI 處理 20% 的核心需求，而剩下的 80% 長尾需求，將由 Agent 透過 CLI 在後台自動完成。

## 重點摘要
- **CLI vs GUI 的本質差異**：GUI 將能力包裝成頁面與按鈕，適合人類點擊；CLI 將能力還原為「明確的動作 + 參數 + 結果」，是天然適合 AI Agent 理解和執行的介面。
- **打破 MCP 與 CLI 的對立迷思**：
  - **Function Calling (FC)**：模型表達意圖的協定（模型說要調用什麼）。
  - **MCP (Model Context Protocol)**：系統側的接入協定（工具如何被統一註冊和發現，解決整合的 N*M 難題）。
  - **CLI (Command Line Interface)**：能力側的執行層（系統能力最終以什麼動作形態被執行）。
  - **Skills (技能/提示詞)**：工作流的編排層（先執行什麼指令，失敗了怎麼辦）。
- **平台 CLI 改造的邏輯**：不是要做一個「黑畫面版」的軟體，而是把「查詢、權限、操作」等原子能力，變成一組能讓 Agent 的 Skill 順手調度的動作說明書。
- **超級 Shell 模式**：相比為每個功能顯式定義一個繁瑣的 Tool Schema，更進階的做法是只給模型一個「執行 Shell」的超級工具，讓模型透過 `指令 --help` 自行探索並組合任務，這極大降低了上下文的負擔。

## 值得深思的問題
- 在開發「知識蒸餾 CLI」工具時，我是否將所有功能都做成了原子化、參數化、可組合的命令？未來這套 CLI 能否無縫接入我自己開發的私人 AI Agent 工作流中？
- 企業內部的 SaaS 系統未來是否都會面臨「雙面孔」的需求？即：給員工看的極簡 GUI 面板，以及給企業 Agent 用的全功能 CLI API 接口庫？
