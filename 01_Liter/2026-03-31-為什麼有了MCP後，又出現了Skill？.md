## 核心洞察

> MCP 解決了 AI 連接外部世界的標準化問題，卻引發「上下文災難」；Skill 通過「漸進式披露」重構 AI 的認知架構——從「能做什麼」跨越到「做得準、做得省」。

## 重點摘要

**MCP 的成就與局限**
- 解決「M×N問題」：曾需要 M個AI應用×N套定制集成 → 統一標準協議
- 類比：如同 USB-C 統一充電標準
- **致命問題**：每個 Server 把所有工具定義一次性塞入上下文
  - 每個工具定義：約 500-800 個 token
  - 每個 Server：通常含 10-20 個工具
  - **真實案例**：配置7個 MCP Server → 未輸入提示詞前已占用 **67,000 個 token**（上下文視窗三分之一）

**效率對比：MCP vs Skill**
| 任務 | MCP | Skill | 差距 |
|------|-----|-------|------|
| 發布文章到社交媒體 | 50,000+ token（7-8次交互） | 數百 token（直接執行腳本） | **100倍以上** |

**Skill 的三層漸進式披露**
| 層次 | 加載時機 | Token 消耗 |
|------|----------|------------|
| 元數據層 | 啟動時 | ~100 token |
| 核心指令層 | 執行時 | 按需加載 |
| 參考資料層 | 遇到難點時 | 按需拉取 |

**MCP vs Skill 的定位**
- **MCP** = AI 的「感官和四肢」→ 連接外部世界（實時數據、第三方接口）
- **Skill** = AI 的「大腦和工作手冊」→ 沉澱內部邏輯和標準流程
- 兩者**互補**，成熟 Agent 架構缺一不可

**產品經理角色轉變**
- 從「寫 PRD」→ 直接編寫和維護 Skill 包
- 核心問題：**誰來定義 AI 的工作方式**，誰就掌握知識分配和工作流設計的壁壘

## 值得深思的問題

1. Skill 的「漸進式披露」設計，是否可以類比成人類組織的「需知原則（need-to-know）」？對大型 AI 系統的治理有何啟發？
2. 「產品經理直接編寫 Skill 包」意味著 PM 需要具備什麼樣的新技能？這是職能的進化還是分工的重組？
3. Skill 沉澱的是「標準流程」，MCP 接入的是「外部能力」——兩者結合是否就是一套完整的 AI Agent 操作系統？
4. 對於品牌行銷工作，哪些流程最適合 Skill 化？（關鍵詞研究？競品分析？文案審校？）
